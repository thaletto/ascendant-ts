# Use an explicit, versioned Yoga rule set with structured evidence

Yoga evaluation uses one closed, explicitly assembled rule set whose current provenance is `ascendant-yoga` version 2. Definitions are immutable and grouped by source-equivalent name and result description. Each definition owns a stable ID, display name, aliases, classification, formation summaries, required Divisions, and one evaluation strategy. Public consumers can inspect descriptors but cannot register executable definitions at runtime.

Common definitions use a declarative condition tree. Version 2 also adds a generic formation tree for house lords, dispositors, divisions, dignity, conjunction, aspect, exchange, sign properties, lunar phase, day/night, and birth sex. It uses three-valued evaluation: `true` and `false` are established results, while `null` preserves missing context or undefined source terms such as strength and named amsas. Alternative formations keep their own evidence beneath one result. One immutable index over the supplied Chart calculation serves every selected definition, and Effect orchestrates atomic preflight plus ordered evaluation with concurrency four.

The rule set follows the supplied [Astrotalk catalog](https://astrotalk.com/astrology-yoga) for its 300 source rows. Nine rows that depend on Gulika or Mandi are excluded in full. The remaining rows map to 226 definitions after equal names and equal result descriptions are grouped. Formation-specific IDs remain separate when repeated names have different results, including the positive and negative Raja groups. Mercury, Jupiter, and Venus are the fixed natural-benefic set; Sun, Mars, Saturn, Rahu, and Ketu are the fixed natural-malefic set. The Moon is classified from its phase only where a rule names it as a benefic or malefic.

_Considered:_ Python-style decorators and a mutable import-time registry (rejected because inclusion and order become side effects), one Effect service per Yoga (rejected because the dependency graph would grow with the catalog), opaque prose evidence (rejected because applications could not audit absence or format causes themselves), and a public plugin registry (rejected because it would weaken rule-set provenance).
